# Workflow: План → Выполнение → Верификация

_Основа · ≈ 11 мин_

## Зачем этот блок

Самый частый сценарий провала: «попросил → получил → задеплоил → сломалось». Между «получил» и «задеплоил» пропущены два шага: план до выполнения и верификация после.

Антипаттерн «попросил-получил» работает на простых задачах. На сложных Claude уходит не туда, делает 200 строк кода, и непонятно, почему теперь ничего не работает.

Решение — трёхтактный цикл. Это не бюрократия. Это разница между «у меня вайбкодинг» и «у меня случайные коммиты, которые я не понимаю».

После этого блока ты перестанешь бояться «AI всё сломает».

## Антипаттерн: промпт → код в проде

Промпт: «добавь в админку фильтр по статусу студента».

Claude уходит. Через минуту возвращается с 180 строками кода. Изменены 6 файлов. Работает или нет — непонятно. Что именно поменялось — непонятно. Ревьюить нечего, потому что не знал, что ожидать.

Через неделю что-то падает. Не помнишь, было ли это связано с фильтром. Откатить нельзя — слишком много правок одной кучей.

## Такт 1. План

Прежде чем Claude что-то изменит, он формулирует план. В Claude Code — режим plan mode (`Shift+Tab`). На claude.ai — словами: «Сначала составь план изменений. Не пиши код, пока я не подтвержу».

Хороший план содержит:
- Какие файлы изменятся
- Какие новые файлы появятся
- Какие зависимости подтянутся
- Возможные риски / побочные эффекты
- Что НЕ входит в задачу (отсекает разрастание задачи в процессе)

Читаешь план. Лишнее — режешь. Не хватает — добавляешь. Только после этого даёшь добро.

### Шаблон промпта на план

```
Прежде чем писать код, дай план:

1. Какие файлы будут изменены и что именно в них поменяется
2. Какие новые файлы появятся
3. Какие зависимости подтянутся (если будут)
4. Возможные риски и побочные эффекты
5. Что НЕ входит в эту задачу (что мы намеренно не делаем)

Не пиши код, пока я не подтвержу план.
```

## Такт 2. Выполнение

Claude исполняет одобренный план. Не больше, не меньше. Если по ходу видит проблему — останавливается и спрашивает, а не уходит в импровизацию.

Если задача большая — разбивай на этапы и проходи каждый отдельно. «План → код первого этапа → проверил → план следующего этапа».

## Такт 3. Верификация

Главный вопрос непрограммиста: как я пойму, что Claude не нагенерил мусор.

### Чек-лист «8 признаков галлюцинации»

1. **Импорты, которых нет.** Claude импортирует функцию из библиотеки, где такой функции не существует. Спроси: «эта функция точно есть в этой версии библиотеки?». Или попроси запустить.
2. **API, которое не существует.** Особенно с малопопулярными SDK. «А такой эндпоинт правда есть в этой версии?»
3. **Несуществующие пакеты.** `npm install some-cool-thing` — а пакета нет в реестре. Попроси сходить на npmjs.com или показать ссылку.
4. **Цифры из воздуха.** «Это даст +30% конверсии» — на основании чего? Если нет источника — это галлюцинация.
5. **Уверенность без оснований.** «Это лучшая практика» — для кого? кем рекомендовано? Если нет ссылки — приземляй.
6. **Функция, которая «должна работать».** Фразы «должно работать» / «обычно так делают» — сигнал. Попроси проверить.
7. **Слишком красивый код.** Если решение выглядит как из учебника — спроси «это работает в моём проекте? использует ли это мою структуру?»
8. **Молчаливые правки в чужих местах.** Claude поправил файл, который ты не просил. Может быть нужно. Может нет. Проверь diff построчно.

### Минимальная верификация

1. Запусти. Если падает — расскажи Claude что упало, попроси починить.
2. Сделай ровно тот сценарий, ради которого делал. Работает ли?
3. Сделай рядом стоящий сценарий, который не должен был сломаться. Не сломался?
4. Посмотри `git diff` — что именно поменялось. Если изменения в местах, которые удивляют — спрашивай Claude.

## `/rewind` — встроенная перемотка Claude Code

До того, как доставать git — есть инструмент, доступный сразу. Команда **`/rewind`** (или двойное нажатие `Esc`) открывает меню перемотки прямо внутри сессии. Это `Ctrl+Z`, только не для одного файла, а для всей сессии — и для кода, и для разговора.

**Что она умеет вернуть:**
- **Код** — к одному из предыдущих состояний за эту сессию.
- **Историю диалога** — Claude «забудет» всё после выбранной точки.
- **И то, и другое сразу** — самый частый сценарий.

**Как вызвать:**
- `Esc` дважды (быстро) — открывает меню перемотки.
- Или вручную: команда `/rewind`.

В меню выбираешь точку и что именно откатывать: только разговор, только код, либо то и другое.

**Когда использовать:**
- Дал Claude уточнение, он пошёл не туда — `Esc Esc`, вернулся на реплику назад, переформулировал.
- Через 10 минут работы понял, что 5 правок назад было лучше — вернулся туда, дальше пошёл по другой ветке.
- Что-то сломалось, не помнишь после какой реплики — открыл меню перемотки, прыгаешь между точками, ищешь рабочее состояние.

**Чем отличается от git:**

| `/rewind` | git |
|---|---|
| Внутри текущей сессии Claude Code | На уровне всего проекта |
| Откатывает код **и** диалог | Откатывает только код |
| Ничего настраивать не надо | Нужны коммиты до этого |
| Между сессиями не сохраняется | Постоянная история |

`/rewind` — мгновенная страховка внутри сессии. Git — надёжная страховка для долгого срока. Они не заменяют друг друга — работают вместе.


## Git как страховка

Трёхтактный цикл работает только в паре с версионированием. Без git ты не можешь откатить плохой результат — приходится дебажить «по живому». С git каждое исполнение = отдельный коммит, который можно вернуть одной командой.

**Минимум, который нужен непрограммисту:**

```bash
git status                  # что изменилось с последнего коммита
git diff                    # построчная разница
git add .                   # подготовить все изменения к коммиту
git commit -m "что сделал"  # зафиксировать
git log --oneline           # история коммитов
```

**Откат, если Claude всё сломал:**

```bash
git reset --hard HEAD       # выкинуть незакоммиченные изменения
git reset --hard HEAD~1     # откатиться на предыдущий коммит
git checkout <файл>         # откатить только один файл
```

**Эксперимент = отдельная ветка.** Если задача рискованная или ты не уверен, что Claude её осилит — заведи новую ветку. Сломалось — переключился обратно на основную, ничего не потерял.

```bash
git checkout -b experiment  # создать ветку и переключиться на неё
git checkout main           # вернуться обратно
git branch -D experiment    # удалить ветку, если эксперимент не пошёл
```

**Привязка к тактам:**

| Момент | Действие в git |
|---|---|
| Перед сложной задачей | `git status` — убедись, что репо чистый |
| План одобрен | `git checkout -b feature/<задача>` (для крупного) |
| Такт «выполнение» закончен | `git diff` — посмотрел изменения целиком |
| Верификация прошла | `git commit -m "..."` — зафиксировал |
| Что-то сломалось | `git reset` или `git checkout` — откатил |

Claude умеет делать git-команды сам — попроси «сделай коммит» / «покажи последние 5 коммитов» / «откати последний коммит». Главное — чтобы ты понимал, какая команда что делает. Иначе можно легко потерять работу.


## Когда какой такт нужен

| Тип задачи | План | Выполнение | Верификация |
|---|---|---|---|
| Однострочная правка стиля | можно пропустить | да | глаза на результат |
| Новая фича с одним файлом | желательно | да | тест сценария |
| Многофайловое изменение | обязательно | да | полный diff + тест |
| Рефакторинг | обязательно | поэтапно | после каждого этапа |
| Работа с данными в БД | обязательно | в dev/staging | сравнение до/после |

## Какую модель брать

Тарифы Pro / Max дают доступ ко всем трём моделям семейства Claude. Это не косметика — у моделей разный профиль «мозг / скорость / цена», и правильный выбор экономит и контекстное окно, и токены.

| Модель | Когда брать | Чем платишь |
|---|---|---|
| **Sonnet 4.6** | Дефолт. 80% задач: реализация фич, код по понятному ТЗ, переписывание текста, разбор интервью | Базовая цена, базовая скорость |
| **Opus 4.7** | Сложная архитектура, исследование, дискавери (изучение задачи до постановки), глубокая отладка, нестандартная логика — когда задача без очевидного решения | В 5–10 раз дороже Sonnet, контекст съедается быстрее |
| **Haiku 4.5** | Когда план уже ясен и осталось механически отработать: тесты по готовому интерфейсу, доки, расстановка типов, мелкие правки UI | В 5 раз дешевле Sonnet, в 2–3 раза быстрее, но проседает на сложной логике |

### Привязка к тактам

- **Такт 1 (план)** — Opus или Sonnet. Думать = дороже, но окупается тем, что план получается рабочий, без переделок.
- **Такт 2 (выполнение)** — Sonnet по умолчанию. Если задача рутинная и план чёткий — Haiku.
- **Такт 3 (верификация)** — Sonnet. Haiku не справится с поиском нюансов в большом diff.

### Почему это важно

**Контекстное окно конечное.** В одной сессии у тебя ограниченный объём текста, который Claude может держать в голове. Opus «думает» сильнее — больше внутренних рассуждений уходит в этот объём, и окно сжигается быстрее. Если запустить весь длинный проект на Opus — упрёшься в `/compact` или новую сессию вдвое быстрее.

**Цена тоже разная.** Прогон одной задачи на Opus может стоить в 5–10 раз больше, чем на Sonnet. На Haiku — в 5 раз дешевле Sonnet. На длинных проектах разница накапливается заметно.

**Скорость.** Haiku отвечает в 2–3 раза быстрее. На итеративных задачах (правка → проверка → правка) это ощутимо: 30-секундные паузы складываются в минуты ожидания.

### Как переключать

В Claude Code: команда `/model` → выбор из списка. Можно менять в середине сессии. Типичный сценарий:
1. `/model opus` — обсудили план
2. `/model sonnet` — исполнили
3. `/model haiku` — расставили тесты и обновили доки

### Антипаттерны

- **«Всё на Opus»** — выжигает контекст и лимиты Pro за пару часов. Opus только на тех тактах, где он реально нужен.
- **«Всё на Haiku ради экономии»** — на сложной логике Haiku ошибается чаще. Время на исправления съест всю экономию, плюс растущее раздражение.
- **«Не переключаюсь, мне лень»** — сессия 4 часа на одной модели = ты переплачиваешь или недоплачиваешь качеством. Привыкнуть переключаться через `/model` — навык первой недели.

## Практика к вебинару

1. Возьми задачу средней сложности из своего проекта (не однострочную).
2. Запусти Claude Code в plan mode (Shift+Tab).
3. Получи план. Прочитай. Найди минимум одну неточность или пропуск.
4. Уточни план. Получи новый. Подтверди.
5. Дай исполнить.
6. Пройди чек-лист верификации.

На вебинаре обсудим, что нашли в планах. У всех 1–2 пропуска с первого раза — это норма.

## Чек-лист готовности

- [ ] Я прочитал план до того, как Claude начал исполнять
- [ ] Я понимаю, какие файлы изменились
- [ ] Запустил результат — не падает
- [ ] Целевой сценарий работает
- [ ] Соседний сценарий не сломался
- [ ] В diff нет изменений в неожиданных местах
- [ ] Удивления озвучил Claude и получил объяснение
- [ ] Закоммитил отдельно (если задача = один коммит)
- [ ] Знаю про `/rewind` (Esc+Esc) — мгновенный откат сессии до git
- [ ] Знаю минимум: status, diff, commit, reset, checkout
- [ ] На рискованной задаче делал отдельную ветку
- [ ] Понимаю, какую модель брать на какой такт (Sonnet/Opus/Haiku)
- [ ] Хотя бы раз переключал модель через `/model` внутри одной сессии
