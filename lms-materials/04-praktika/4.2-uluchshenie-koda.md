# Улучшение существующего кода

_Практика · ≈ 8 мин_

## Зачем этот блок

Сборка с нуля — это 20% реальной работы. 80% — это итерации над тем, что уже есть. Чужой репозиторий, твой собственный код двухмесячной давности, старый код (легаси), в котором страшно что-то трогать.

Подход «попроси Claude добавить фичу» работает на пустых проектах. На существующих — ломает соседнее. Этот блок про то, как этого избежать.

## Сначала — понять, потом — менять

Главная ошибка: попросить Claude добавить фичу, не объяснив архитектуру. Он угадывает, ставит по соседству с тем, что нашёл, и часто ломает уже работающее.

Правильный порядок:
1. Дай Claude карту проекта.
2. Попроси описать, как сейчас работает релевантная часть.
3. Только потом проси менять.

### Шаг 1. Карта проекта

Если CLAUDE.md уже есть — отлично. Если нет — попроси Claude его сгенерировать:

```
Прочитай структуру проекта. Сгенерируй CLAUDE.md по шаблону:
- что это
- стек с версиями (взять из package.json / requirements.txt)
- структура папок с назначением каждой
- соглашения, которые ты заметил в коде
- что-то, что выглядит как антипаттерны проекта
```

Прочитай результат. Поправь руками то, что Claude угадал неточно.

### Шаг 2. Описание текущего поведения

Перед изменением фичи — попроси Claude описать, как сейчас работает.

```
Прежде чем менять что-либо, опиши:
1. Какие файлы участвуют в работе фильтра по статусу студента
2. Какие данные он получает на вход
3. Что происходит при каждом значении статуса
4. Где он используется (вызовы из других мест)

Не пиши код. Только описание.
```

Если описание совпадает с твоим пониманием — можно менять. Если нет — у тебя пробел в понимании, который надо закрыть до правок.

### Шаг 3. Только теперь — изменения

С планом (см. core-4-workflow), по этапам, с верификацией после каждого.

## Виды итераций

### Багфикс

Проще всего, если есть текст ошибки и шаги воспроизведения (см. core-5-debugging).

Антипаттерн: «исправь баг в фильтре». Без воспроизведения Claude гадает.

Правильно:
```
Баг: при выборе статуса "архив" таблица не обновляется,
показывает все статусы.

Воспроизведение: открыть /students, выбрать в фильтре "архив",
видим всех студентов вместо архивных.

Ожидание: видим только архивных.

Файлы участники (по предыдущему шагу): components/students-filter.tsx,
hooks/use-students.ts, app/students/page.tsx.

Не правь, пока не сформулируешь гипотезу.
```

### Рефакторинг

Самое опасное. Меняем форму, не должны менять поведение.

Правила:
1. Перед рефакторингом — зафиксируй поведение тестом или скрином сценария.
2. Делай маленькими шагами. Один шаг = один коммит.
3. После каждого шага — запуск, проверка ключевых сценариев.
4. Если есть тесты — запускай после каждого шага.

Шаблон:
```
Зарефактори функцию X в файле Y.

Цель рефакторинга: <зачем — читаемость, переиспользование, etc>
Что НЕ должно поменяться: поведение функции (вход → выход).
Что НЕ должно поменяться: публичный API (имя, сигнатура).

План рефакторинга:
1. <первый шаг — самый маленький>
2. <второй шаг>
...

Делай по одному шагу. После каждого жди подтверждения.
```

### Новая фича в существующем коде

Опасность: Claude может «улучшить» соседние места, которые ты не просил. Защита — явный запрет.

```
Добавь фичу X.

Можно менять: файлы A, B (если нужно — спроси разрешения).
Нельзя менять: всё остальное. Если кажется, что нужно — остановись и спроси.

Стиль кода: следуй текущему (см. CLAUDE.md, посмотри соседние файлы).
Не вводи новые библиотеки без согласования.
```

### Чужой или старый код (легаси)

Особенности:
- Соглашения проекта могут отличаться от общепринятых. Claude часто пытается «исправить» под общепринятые. Останавливай.
- Документация может быть устаревшей. Доверяй коду, не комментариям.
- Тесты могут быть слабыми или их может не быть. Перед изменениями — добавь хотя бы один приёмочный тест на сценарий, который не должен сломаться.

## Когда не итерировать, а переписать

Сигналы, что итерация дороже переписывания:
- Каждое касание ломает три других места
- На простую фичу уходит больше времени, чем заняло бы переписать модуль
- Тесты невозможно написать из-за переплетения зависимостей
- Сам автор кода (если это ты) уже не понимает, как это работает

В этом случае:
1. Зафиксируй контракт текущего модуля (вход, выход, побочные эффекты).
2. Перепиши с нуля рядом, не трогая старый.
3. Переключи использование на новый.
4. Удали старый.

Claude отлично помогает с шагом 1 — попроси «извлеки контракт модуля».

## Практика

Возьми старый свой проект (или чужой репо). Шаги:
1. Сгенерируй CLAUDE.md.
2. Попроси описать одну фичу.
3. Внеси одну небольшую правку через план + верификацию.
4. Зафиксируй, что нашёл по ходу описания (в антипаттерны CLAUDE.md).

## Чек-лист готовности

- [ ] В корне проекта есть актуальный CLAUDE.md
- [ ] Перед изменениями попросил Claude описать текущее поведение
- [ ] Использовал plan mode на нетривиальной правке
- [ ] Изменения сделаны маленькими шагами с коммитами
- [ ] Целевой сценарий после правок работает
- [ ] Соседние сценарии не сломались
- [ ] В diff нет молчаливых правок «по соседству»
